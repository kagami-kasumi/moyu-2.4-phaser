# 任务与状态维护

任务必须服务于一项可观察结果，避免“完成全部逆向”“完善全部系统”。功能线用来记录连续目标，不要求预先枚举游戏所有系统。

## 下一任务生成责任

同一对话可连续承载多个 task；任务数量不受对话数量限制。用户在当前对话要求开启下一项，即可直接切换到下一项，无需重新校验上一项是否完成、重新确认或新开对话。以已落盘调度继续工作，任务内的功能验收按当前合同执行。

用户明确说“完成下一任务”时，直接执行当时下一个 Ready 项；相同对话或相同 `/goal` 文字不代表要求检查旧任务。具体选择与自动续跑的绑定规则以[执行协议](agent-protocol.md#调度)为准。不得将旧任务完成状态审计作为下一任务的前置工作或本次交付。

下一任务由主 agent 负责选择和生成，不把常规排期交还用户。完成当前任务的收尾必须检查已有队列；有合法后续任务则补齐并激活，没有则根据 TASK_OUTLINE.md、当前覆盖缺口、已确认源入口及依赖，自主生成一个下一任务的独立合同、覆盖台账与 state.json 记录。选择理由写入新合同，优先补齐当前玩家旅程的实际缺口，不为方便通过测试而挑选无关小修，也不预建大量空任务。

队列为空只表示已定义任务已完成，不代表游戏完成。收到“执行/继续”时若没有当前项，先按上述规则生成并调度，再执行这个新任务，不因空队列要求用户从几个常规方向中选择。有 Blocked 当前项时继续处理阻塞，不借生成新任务绕过。

生成前做足以明确输入、直接依赖和验收的有界只读调查；Ready 不要求全量逆向已经结束，剩余取证属于任务内部里程碑。实际缺少文件、外部依赖或只有用户能决定的产品范围冲突时，记录具体阻塞并只询问必要信息；不能把通常的实现顺序选择当作用户裁决。

任务收尾生成下一任务不等于自动执行下一任务：普通单任务请求将下一项设 Ready 后交回；用户明确要求连续执行或多个任务时按授权继续。只有核对项目路线和覆盖证据确实无剩余交付，或用户明确停止扩展，才可不生成后续，并说明依据。选定方向仍受用户之后的明确指定覆盖。

## 当前项目主线约束

2026-10-06用户指定先全量数值/内容注册，再开始选角色和完整存档，之后按物品机制、区域与任务链推进，详见TASK_OUTLINE.md。生成下一项须服务该顺序；基础交付完成前不恢复逐道具扩展。基础完成后以注册覆盖缺口组织完整机制包/区域包，现有未完成小合同需保留全部验收并有据合并，不因单个道具易验收而另起功能线。

## 默认粒度

2026-10-07用户针对现有任务明确要求适度拆分：当前基础线按修订后的015/017/018/019/020/021/016/022合同执行，覆盖迁移见LINE-GAME-FOUNDATIONS。每项只承担明确的数据域或可用能力，身份目录、数值规则、字段合同与运行时集成可分别验收；不按单个物品/字段/测试步骤细拆。发现相邻系统工作应归入其所属后续合同，不能因“完整基础”重新并回当前任务。以下默认原则不得推翻本次明确拆分。

任务按完整能力或玩家旅程划分，同一交付所需的有界取证、资源转换、实现、回归与视觉验收放在一个合同中。内部里程碑只控制先后顺序，不新增调度项；完成中间报告、工具或工程骨架不算任务完成。预计耗时长、文件多或发生上下文压缩不是拆分理由。

只有存在可独立交付的新能力、无关系统或真实外部依赖时才拆分，并说明各包的独立验收价值。合并未执行任务时保留已有完成记录，迁移全部验收要求和依赖，记录旧编号去向，不能把被合并项标为 Done。

含逆向与实现的任务按最终交付归为 implementation。Ready 要求调查范围、源入口和验收方法明确；实现所需的 verified 数据可在本任务取证里程碑形成，但未确认关键事实前不得开始对应实现。Planned 任务仍需在激活前补齐有界调查范围，不能用“全部逆向”替代输入。

## 唯一状态

[state.json](../tasks/state.json) 保存功能线、任务和治理项。看板和队列是工具输出，不编辑其状态。新任务至少包含 `id/title/line/status/type/dependsOn/definition/completion/blocker`。

- 新任务默认 Planned；只有输入可用、依赖 Done、验收明确时可设 Ready。
- Ready → Active → Done；实际阻塞时 Ready/Active → Blocked，解除后 → Active。
- 任务撤销或范围拆分需说明原因并修订依赖；不要把未做的任务设 Done。
- Done 必须有摘要、真实通过的检查和现存证据路径。失败或未运行的检查写在报告中，不能填成 passed。
- 有未完成任务时，恰好一条 Active 线、一个当前游戏任务；治理当前项最多一个。Blocked 占当前位置。
- 治理项只有真正妨碍当前执行的 harness 问题才创建，其合同仍使用同样六个章节；当前默认没有治理项。

## 合同模板

每个 task 放在 `docs/tasks/task-definitions/<ID>.md`，必须具备以下章节：

```markdown
# TASK-类别-编号 · 名称

## 目标
一个可验证结果。

## 输入
精确源文件/已完成合同/证据路径和已知限制。

## 范围
本次工作包、写入文件和明确排除的邻接系统。

## 输出
可交付文件与其消费者。

## 验收
要执行的实际命令、可观察行为、源对比；命令必须已经存在或由本任务创建。

## 停止与拆分
实际阻塞条件、超出范围时的拆分办法、未知项处理。
```

不要把固定时间或上下文压缩次数写成停止条件。后续 Planned 合同可以列明待确认项，但激活前必须用源证据补齐；不能将空白的验收交给执行 agent 自由发挥。

修改状态后 `npm run generate:harness`；修改合同/文档后 `npm run check:harness`。初始工程尚未存在，不要求不存在的构建/测试命令。新增构建能力时同任务更新质量门禁和命令。
